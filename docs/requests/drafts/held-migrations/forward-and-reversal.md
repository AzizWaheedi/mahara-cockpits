# Held request-policy migration and reversal

The adjacent CLI-generated migration is a candidate only. It is deliberately outside `supabase/migrations`; do not copy or apply it to any environment until the current code, UI, migration runner and exact live metadata have been independently reviewed and rehearsed. The older unversioned planner is also outside that directory and must never be deployed. This branch is not release-ready.

The migration starts one explicit transaction, takes locks and checks the specific live functions, ownership, security mode, grants, search paths, type-table triggers, table column signatures, row-level security and table grants observed on 6 November. It refuses missing or future snapshots, snapshots with inconsistent key/version or unexpected policy markers, existing v1 functions and an existing readiness setting. It adds no readiness setting, so new behavior remains off. Lock acquisition has a short timeout; a timeout or drift should roll back the whole transaction. A migration runner must be verified to honor this transaction and must not partially apply its statements. All five cockpit builds, including stale tabs and the kickoff caller, need testing before readiness can ever be enabled.

The file was generated with Supabase CLI 3.0.0 using `migration new` in the isolated worktree and moved into this held folder. [Supabase CLI v3](https://supabase.com/changelog/supabase-cli-v3) defaults database commands to local and requires explicit remote targeting and confirmation for hosted writes; a successful local command is not proof of a hosted release.

Offline tests confirm that missing expected functions cause refusal before new columns or functions appear. A separate PGlite rehearsal runs the complete candidate against synthetic tables and functions, with the fixture's metadata fingerprints substituted in memory and its kickoff dependency stubbed. It checks default-off behavior, a legacy submit, pre-activation transaction rollback and function-grant drift refusal. This is not an independently executable downgrade or an exact production clone. Table lock ordering, worker interactions, the real kickoff caller, live-state recheck and an exact matching-state rehearsal remain open. The captured hashes are deliberately strict and will be stale if another release changes any checked definition. Rebase and independently review rather than weakening a failing guard.

## Rollout and rollback

1. First rehearse the entire file and its exact rollback in a disposable PostgreSQL database with matching function definitions, table schemas, grants, triggers and representative synthetic history. Test both lock orders, failed installation rollback, queue repair and worker behavior, and the legacy and v1 UI/RPC paths. Verify the precise deployment tool, transactional behavior and recovery under timeouts. Take a restorable backup and confirm the current database state and pending writer actions immediately before any eventual release.
2. Deploy the reviewed server and client code with readiness absent and all request types on `legacy`; verify normal request creation and provider reconciliation before activation. Only after the full UI and kickoff paths are confirmed should an authorized editor create an audited v1 type version. A readiness change by itself must never turn any type on.
3. To stop new v1 requests after activation, set readiness false and create an audited new `legacy` type version. Keep the v1 functions, snapshot cutoff and all historical versions: accepted v1 requests and missing queue payloads can still be replayed. Reconcile in-flight calls, unknown provider outcomes and any waiting work; switching the flag cannot undo an external task.
4. A full schema downgrade is a separate, unimplemented operation, not the off switch. Before drafting its transaction, prove that no v1 snapshots, accepted requests, queued or in-flight work, replays, or unknown external effects can depend on the new code. Hold new writes, drain and reconcile queues, verify the exact deployed definitions and privileges, and test a drift-guarded restoration of the original functions and ACLs without deleting history. If any v1 history remains, retain the compatibility code; do not force a downgrade.

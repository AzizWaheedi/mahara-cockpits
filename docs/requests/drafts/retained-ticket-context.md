# Retained ticket context: review and release notes

Status: isolated candidate only. The request-type settings are not changed by this branch, and no live migration or provider action has been performed. The two types already have one-tap kickoff mappings; their optional `details` question is a separate, versioned settings edit.

For a routed old ticket in either affected type, the saved description excerpt is retained under its own label and sent to the destination team. This is the trimmed first-import snapshot, up to 4,000 characters, not necessarily the full or current ClickUp description. The request form presents editable additional notes separately. Empty notes do not remove the saved context. If the notes equal the saved excerpt after trimming, the text appears once; otherwise both are kept, even if the notes quote some of the excerpt. A stale routed-ticket error requires review and is not silently retried as a standalone request. Existing request versions and already-materialized queue payloads are not rewritten. The sweep can reconstruct an already-submitted part whose queue row is missing using the new planner, so that part's eventual description can change; inspect those states before release.

## Dependencies and release order

1. Re-read the live request type versions, fields, planner source, privileges, writer, deployment state and active work; confirm no other release is in progress. Resolve independent security and UX review findings, including the behavior of in-flight request retries. Inspect the changed files for private data before publishing.
2. Rehearse the CLI-generated migration in an isolated database against a fresh function and grants read. Its pre-guard checks the exact reviewed function definition and owner, ACL, security mode, volatility and search path; its post-guard checks the exact replacement and the same security attributes. A changed function or privilege stops the migration. Confirm rollback and any concurrent pending request effects. It does not edit request-type settings.
3. Deploy the reviewed database change before any cockpit that promises retained context. Deploy and verify all five cockpit forms before exposing the new questions to their users. Review the screens, keyboard and accessibility behavior in the actual supported workflows. Do not assume the database alone changes the visible form.
4. Only after the preceding steps pass, add one versioned optional `details` question to each targeted type through the audited settings save with current version checks. The earlier design proposed the label `What happened?`; it is not a recorded separate user sign-off. Confirm the systems-manager overlap and SOP wording separately. Recheck one-tap eligibility and the types' complete field mappings. Old queued work remains frozen.
5. Plan a clearly labeled internal canary and review the exact provider effects and cleanup first. Do not send or create test tasks without the applicable authorization, and preserve the user's prior decision not to send a second workflow WhatsApp test. Verify the saved request and actual provider readback; a synthetic queue is not a ClickUp receipt.

Keep the existing Typeform/Make ownership and native switches unchanged; the request context repair does not authorize a cutover. Rollback requires an independently checked reverse migration and coordinated UI/settings strategy that preserves any request versions and work already filed; deleting version history or rewriting queued tasks is not a rollback.

The draft retry registry is in memory and scoped to the Supabase client and signed-in user ID. For a replacement it verifies the seat with Supabase Auth, pins that seat's token to the individual database request, and refuses to start if the signed-in account changes before sending. A confirmed first database refusal or a failure before the request is sent permits a corrected retry; an earlier uncertain outcome still keeps the original request ID and prevents an edited resend. A named synthetic UI test emits real auth events through the mounted provider, and a separate test exercises token pinning through the installed Supabase SDK with a fictional fetch. They are not live authentication or provider checks. An already-sent request can complete under the original account after sign-out, but the old component must not show its result in the next seat.

The in-memory registry does not coordinate tabs, devices or browser reloads. The live submit function locks the imported ticket row before routing, which appears to prevent two concurrent routes of that same ticket; verify it with two actual concurrent transactions and test failure/recovery before relying on that guarantee. The registry is keyed by user ID, not session generation, so sign-out and re-entry as the same user need further review. Independent authentication and provider verification, the other cockpit typechecks, guarded rollback, and an explicit safe recovery path remain required. Do not ship the draft until those limits are resolved.

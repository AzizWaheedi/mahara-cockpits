# GitHub App relay adapter: disconnected candidate

This is an offline candidate, not a release or an integration into `worker.ts`. No App has been registered, installed or connected. The normal static-token worker, read-only doctor, native apply switch and provider permissions remain unchanged. This worktree starts at `main` commit `9f50c1ce`, after PR #190; reconcile with the then-current main before any release work.

`makeAppDispatcher` opts in explicitly and rejects mixed static-token mode and a mismatched repository name. It copies its trusted config and snapshots the dispatch payload before asynchronous work. The candidate mints a token only through an injected port, with one configured installation and repository ID, a fixed GitHub endpoint, redirects refused, Contents write, bounded response reads, sanitized errors and no token in ledger rows. It validates the returned token, expiry, permission and repository metadata before reusing the existing dispatch adapter and ledger. Mint errors cannot send a dispatch; an attempted dispatch retains the existing definite/unknown outcomes. Keys and token are passed only in memory. Neither port has a default network adapter.

## Release blockers

- Owner action: the owner must install a reviewed App on only the target repository, with Contents write. This permission allows more than dispatch. The App private key can access everything in its installation, regardless of the narrower token request.
- Scope and fields in actual GitHub token responses are unverified. The current strict validation fails closed if the provider omits them; it is not evidence of live compatibility. A controlled, authorized non-client provider test and an independent security review are necessary.
- This is not wired into the worker, has no real configuration mode, no installation registry, no reviewed private-key file loader, rotation or process isolation, and no operator-facing diagnostics. Do not put PEM material through the current generic env parser. The read-only doctor must not mint a token.
- The real relay claims up to five rows before dispatch. Even though mint errors mean no dispatch, its current failed outcome consumes attempts. A pre-claim readiness check and a safe, operator-visible pause/recovery mechanism are required before integration; neither is implemented here.
- Receipt inserts are not cancellable. On a timed-out insert, a late intent can be stored even if no call left, and a late response receipt can race a best-effort unknown receipt. Recovery must distinguish these cases and allow out-of-order rows. This candidate does not claim a complete deterministic audit trail, or that a terminal receipt survives process exit. A complete design must bound receipt operations without false evidence, preserve the no-intent/no-call rule and reconcile ambiguous dispatches without retrying them.
- Native onboarding and research publication remain separately blocked by response provenance, the existing Typeform consumer, safe publication, operational canary and cutover checks. A credential does not resolve those issues.

## Verification

The two explicit candidate test files and `hermes/forms-relay/relay.test.ts` use synthetic keys, fake identifiers and injected fake providers only. The tests cover payload snapshots, fixed target and scope, mode and binding refusal, receipt-before-mint, timeouts and late response cleanup, sanitation, existing dispatch success/refusal/unknown behavior, and unchanged relay dry-run behavior. They do not exercise GitHub or prove production key storage, process-death handling, concurrency safety or a real provider response.

## Pre-claim and recovery model on current main

This separate worktree starts at current `main` commit `9f50c1ce`; it does not rebase or modify the earlier candidate. `guarded-run.ts` is a disconnected protocol model. It is off unless explicitly enabled, verifies and probes a single bound token before reserving at most one row, validates all clock samples and token lifetime, then requires a fenced start before dispatch. Every injected operation is deadline-bounded. It returns a fixed hold reason and never returns token or exception text. Faked unavailable, malformed, expired and wrong-repository credentials are held without reserving a row. Late successful preflight or reservation is not followed by a send. This does **not** establish that real credentials, especially credentials revoked after the check, will never consume a real attempt.

The intended operator screen should show the fixed hold reason, timestamp, whether the hold write was confirmed, and a link to the unresolved operation, without credentials, payloads or exception text. `hold_unrecorded` requires an independent fail-closed shutdown and alert; it does not prove that a durable pause exists. Recovery is modeled as a fresh readiness check followed by a single transaction that compares the hold revision, verifies that every uncertain claim and external effect has been reconciled, and then clears the hold. An uncertain resume needs human inspection rather than a retry. The operator must establish that no timed-out worker or provider request can still perform an effect before resolving an unknown action.

The required database operations are **not implemented**: reservation must atomically check the same durable hold; begin must atomically check that hold, current owner, matching lease and claim, and commit a `dispatch_started` fence; restoring a pre-start claim and its prior attempt state must atomically establish the hold; finalizing a refused/uncertain started action and establishing its hold must be atomic. Timed-out mutations can commit late and receipts can arrive out of order. The `fence-model` is a sequential in-memory thought model, not a PostgreSQL concurrency or crash-safety test. Owner-switch locking, worker death, lease expiry versus late sends, service-role permissions and actual durable audit need a database migration, security review and realistic race tests. Real GitHub verification and credentials, token minting and private-key storage are not connected to this protocol model. GitHub authorization failures after the start fence may still consume an attempt; do not represent the zero-consumption guarantee as complete.

Bounded response reads do not bound the existing dispatch ledger's receipt inserts. The mint adapter also permits terminal receipt writes to finish late after its deadline. These cases are **release blockers**. A provider dispatch that might have left remains unknown and cannot be retried blindly; cancellation alone is not proof that it did not occur. No production changes or provider requests were made.

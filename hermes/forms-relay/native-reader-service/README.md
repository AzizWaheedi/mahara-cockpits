# Native research reader HTTP candidate, offline only

This directory is not a deployed service. It contains no server, real database or ClickUp adapter, secrets, configuration, migration, sender integration or production entry point. Nothing here switches either form on. The production form ownership and Typeform/Make workflows must remain unchanged until the entire cutover is verified.

The candidate models these boundaries:

1. A disabled-by-default handler permits only a bounded JSON POST and checks a signed GitHub OIDC identity for the pinned repository, owner, workflow, commit, ref, protected environment and event. A real deployment needs an independently managed rate limiter and a platform gateway compatible with GitHub OIDC.
2. A response-bound 256-bit capability is hashed; the injected database port must atomically check and bind the exact task, response, version, receipt, identity, state, expiry, latest submission and retry count. This candidate cannot prove those checks because its port is a fake. A failed provider check comes after the capability is bound, so a durable bounded same-run retry and an explicit reconciliation state are required.
3. Only after that binding does an injected provider port read the specified comment. Its actual adapter must independently verify task association, enforce provider response limits and timeouts, and never log data. The handler hashes the returned bytes and compares the pinned digest. A second database transaction must recheck the binding, currentness, capability, receipt and approved schema fingerprints after the provider read. Neither port is implemented here.
4. The handler denies unexpected response fields, invalid shapes, duplicate refs, mismatched schema/printer fingerprints or absent validation attestations. It also requires an explicitly configured per-version ref/title allowlist; nothing is implicitly approved, and a missing or unexpected ref is denied. The production allowlist and handling of retained free text must be reviewed, because even a permitted field can contain sensitive information. Those attestations are only meaningful if the real, narrowly privileged database function validates the complete raw answer object under the pinned versioned schema, rejects unknown or invalid fields, confirms the actual printer definition, and returns only approved fields. Exact live schema hashes and the production data-retention/privacy policy have not been established. The database adapter must convert its timestamp into a genuine UTC instant using the exact canonical format `YYYY-MM-DDTHH:mm:ss.sssZ`; the candidate rejects impossible dates, noncanonical values and unnormalized PostgreSQL timestamp text.

No real client-field allowlist is provided in this candidate. Each returned field must have an exact allowed ref and title; unknown, duplicate or changed refs and titles fail closed. A missing answer is not detected by this allowlist because some fields are optional. Only complete validation of the underlying raw submission and its printer at the trusted source can establish what should have been returned. A synthetic test demonstrates rejection of a phone field unless it was explicitly allowed. Client needs, all appendix fields, access rights and retention require a deliberate decision before configuring this handler. Neither allowlisting nor removing phone fields proves that retained free text is free of personal information.

The handler rejects unexpected top-level snapshot fields and blank printed values before reading the provider comment. The mapper separately prepared for the private worker preserves the legacy contact and appendix fields; this candidate has no approved policy that authorizes returning those fields.

The wire timestamp has millisecond precision and can lose database microseconds. It is display metadata only and must never be the sole response identity or ordering key. Freshness needs a database-enforced, deterministic ordering with a tie-breaker, checked inside the actual transaction.

The key-fetch candidate pins `https://token.actions.githubusercontent.com/.well-known/jwks`, rejects redirects, oversized or malformed payloads and duplicate key IDs, and does not reuse an expired cache after an error. It aborts stalled headers and body reads after five seconds in synthetic tests. It caches for five minutes; a newly rotated signing key can be rejected until the cache expires. It has not been tested against a real GitHub endpoint. A real network adapter must handle DNS and TLS securely, use an independently reviewed timeout, cache and provider error policy, and never log keys, tokens or request content.

The second database check reduces stale reads but does not serialize later external publication with new submissions. A response can still be superseded immediately afterward. The report publication fence, provider-side idempotency and unknown-outcome recovery remain unimplemented, so this candidate must not be deployed or used to justify the native switch.

## Transactional source candidate

The separate CLI-generated migration `supabase/migrations/20261105162937_native_research_source_reader_candidate.sql` is a local review candidate, not an applied migration. It creates an unexposed private schema with a default-off gate and no execute, schema or table grants to `anon`, `authenticated` or `service_role`. Its new dedicated reader role has no login or members. Its only explicit grants are schema usage and execution of this one function; it has no direct table privileges. PostgreSQL's inherited `PUBLIC` privileges also need an effective-permissions audit before any login or membership is provisioned. No application identity or capability issuer is provisioned. An authorized operator must separately review and create a narrowly scoped server identity, capability issuance and independent rate limiting before it could be connected. A general service-role key is not a substitute for a restricted identity.

When deliberately enabled in a synthetic database, the function binds a 32-byte response capability to a single run and attempt, checks expiration against the wall clock, records up to six committed reads, locks the existing response, invite, effect, queue receipt and version rows, checks the current response against newer live onboarding submissions from any source, and validates a canonical stored answer object against the pinned v2/v3 schema and exact validator definitions. If another response has an equal or missing submission timestamp, it refuses to guess which one is later. It refuses versions containing file or date fields. The observed v2 and v3 onboarding schemas have no such fields; the Drive link is a URL text field. The function checks that the submitted-answer immutability trigger is present and enabled, renders with pinned printer definitions, and requires the resulting complete comment to match the effect plan and delivered queue digest. The service must still fetch the exact task comment and compare its bytes before exposing the snapshot.

The handler passes the original capability only to its trusted database port; the function decodes and hashes it internally. The `source-port.ts` adapter maps the exact binding to parameterized SQL, but supplies no database driver or transaction implementation. Its injected gateway must commit before resolving and must not log the capability. Both the initial read and post-provider recheck must commit before their results are released, and the complete returned snapshots must agree. Each consumes one of the six committed reads.

**The SQL read counter is not a durable abuse limit by itself.** PostgreSQL returns a function result before a caller commits, so a direct database caller can read and roll back repeatedly without consuming a use. This is reproduced by a synthetic test. Activation requires a trusted gateway that owns the restricted database connection, commits before releasing a result, never exposes its connection credentials, and enforces an independently durable rate and replay limit. Transaction or connection errors after a possible commit must be reconciled, not blindly retried.

## Committed gateway candidate

The separate local migration `supabase/migrations/20261105164639_native_research_gateway_reservations_candidate.sql` adds a private per-capability, per-run reservation ledger. `gateway.ts` implements the transaction boundary against an injected, server-owned connection pool: it verifies the restricted database role, commits one reservation before reading, then commits the source transaction before returning any snapshot. Failed reads still consume their committed reservation. Both the initial read and post-provider recheck require a reservation, with at most six committed reservations per capability and run. Lost commit acknowledgments produce a generic failure with no automatic retry; operators will need a separate reconciliation procedure.

This is not a deployed service and supplies no configured database pool, login, issuer, credentials or network policy. The runtime must exclusively own and hide the restricted database connection, lease an exclusive connection whose idle status the driver actually verifies, enforce a separate global rate limit, and verify cancellation, finite acquisition/query/rollback deadlines, and connection quarantine. The driver must expose actual PostgreSQL `BEGIN` and `COMMIT` command tags. The local PGlite direct fixture does not expose those tags and labels its synthetic successful calls; a separate in-memory node-postgres test exercises actual protocol tags. Production tag behavior remains untested. A direct caller with those database credentials can invoke `read_source` without reserving and can still roll back its transaction; the reservation ledger protects only calls that pass through the gateway. Do not treat its local tests as proof that production connections are inaccessible. The native handler, onboarding switch and publishing remain off. The source/publication fence and provider recovery are still required.

`pg-driver.ts` adapts an exclusively owned node-postgres 8.21+ pool. It checks that the socket reports encryption, authorization and the expected SNI, and rejects a privileged/inheriting login, extra role memberships, a non-idle connection, effective direct table/view or sequence access, schema creation privileges, callable non-trigger security-definer functions, and logging settings that could expose query parameters. It audits both the login and assumed reader role, checks the reader role's own attributes and memberships, and pins the reviewed owner and definitions of its two allowed private functions. It switches only to the NOLOGIN reader role and resets it before reuse. Socket flags and SNI alone do not prove hostname verification: a supplied pool could use a permissive custom certificate checker or unsafe trust roots. A reviewed pool builder that enforces the expected CA, hostname validation and `rejectUnauthorized`, with real-certificate negative tests, is a hard activation prerequisite. The pool and its login may not be exposed to callers. `held-reader.ts` composes the OIDC handler with this narrow pool and gateway, but forces the handler off even if configured on. It creates no listener and has no activation path.

The live project currently grants PUBLIC access to two `net` tables and a sequence. Those inherited privileges make the adapter refuse the current environment. Removing or isolating that access requires a separate dependency and impact review; this candidate makes no grant changes to the existing project. Synthetic in-memory node-postgres tests label a fake socket as TLS only to exercise the code path, so they do not validate real certificates, network isolation, actual login provisioning, backend logging, or pool behavior under production outages. The node-postgres dependency and lockfile must be pinned by the eventual runtime before release.

The unimplemented [PostgREST alternative](POSTGREST-ALTERNATIVE.md) explains a potentially narrower RPC boundary and the commit, authorization and exposure checks needed before it could replace direct SQL.

The database checks establish validity and source provenance under the pinned functions and existing immutability trigger; they do not imply the rendered summary is a byte-for-byte reproduction of the structured answers. The private worker must handle all returned contact and free-text fields under an approved access, retention and logging policy. Exception logging and database bind parameters must not expose capabilities or answers.

**Do not activate this candidate.** There is no capability issuer, authenticated runtime role or provider adapter wired to it. The function locks existing rows but cannot stop a concurrent newer response from being inserted, and the timestamp used for ordering is not protected by the existing immutability guard. A post-provider check and shared submission/publication fence with unknown-outcome recovery remain required. Full end-to-end, multi-connection race and provider tests, reviewed role grants, and fresh live definition and flag checks are required before release. The Typeform/Make route remains live.

The candidate has an eight-second whole-request deadline and passes an abort signal to database, rate-limiter and provider ports. Those adapters must actually honor cancellation and have their own verified deadlines. A timeout after a database or provider operation began is an unknown outcome and needs durable reconciliation, not an automatic retry. The test ports have no such durable state and do not prove production recovery.

## How we know it works

Run only the explicitly named tests:

```
bun test hermes/forms-relay/native-reader-service/auth.test.ts hermes/forms-relay/native-reader-service/jwks.test.ts hermes/forms-relay/native-reader-service/handler.test.ts hermes/forms-relay/native-reader-service/source-port.test.ts hermes/forms-relay/native-reader-service/gateway.test.ts hermes/forms-relay/native-reader-service/pg-driver.test.ts hermes/forms-relay/native-reader-service/held-reader.test.ts
```

Tests use generated keys, fictional identifiers, a fake provider and fake database ports. They do not test provider delivery, deployed credentials, role grants, Postgres transactions, real schema validation, actual rate limits or concurrent production submissions. Source copied from the earlier offline prototype remains experimental.

The source migration also has synthetic PGlite checks in `source-reader.test.mjs`. Set `PGLITE_MODULE` to the local `@electric-sql/pglite` `dist/index.js` and run it with Node. The default run uses stub validators. To exercise read-only captures of the actual deployed schema, title and function **definitions only**, set `REAL_SCHEMA=1`, `ONBOARDING_SCHEMA_FIXTURE`, `ONBOARDING_TITLES_FIXTURE` and `ONBOARDING_FUNCTION_FIXTURE` to local schema-only JSON files and run with `SOURCE_VERSION=2` and then `SOURCE_VERSION=3`. `source-validator-actual.test.mjs` exercises both actual captured schemas against fictional inputs. To exercise node-postgres against an in-memory database, use PGlite 0.5.13, node-postgres 8.21.0 and also set `PG_MODULE` and `PGLITE_PG_MODULE` to their local entrypoints. `pg-driver-public-access.test.mjs` separately verifies that inherited PUBLIC table or sequence privileges are denied. These tests do not read client responses, contact a provider, run against the hosted database, verify real TLS or establish multi-connection concurrency behavior.

## Not in scope

Client data, network provider calls, actual database changes, app installation, secrets, dispatches, publication, deployment and production cutover.
